# Response Patterns

Use these patterns only after the fear has been named.

They are not scripts to hand over early. They are structures that help the freelancer say what they already decided.

## Pattern 1: Separate and Schedule

Use when the request is valid but outside current scope.

```text
Happy to help with [request]. That is separate from [current scope], so I would handle it as [next project / change order / post-launch item]. I can send over [estimate / timing] by [time].
```

Example:

```text
Happy to build the analytics dashboard. That is separate from the Thursday launch scope, so I would handle it as a post-launch add-on. I can send timing and cost tomorrow morning.
```

## Pattern 2: Protect the Shared Priority

Use when the client is asking for extra work before a deadline.

```text
I want [shared priority] to go well. Adding [new request] before [deadline] would put [priority] at risk. The clean move is [next step].
```

Example:

```text
I want Thursday's launch to go smoothly. Adding the dashboard before then would put the launch pass at risk. The clean move is to launch the agreed scope Thursday and start the dashboard after.
```

## Pattern 3: Paid Rush

Use when the freelancer is willing to do the work quickly, but not for free.

```text
I can take this on as a rush add-on. The fee would be [amount], and I would need approval by [time] to fit it in.
```

Example:

```text
I can take this on as a weekend rush pass. The fee would be $1,200, and I would need approval by 5 PM today to fit it in before Monday.
```

## Pattern 4: Support Boundary

Use when project work is turning into ongoing support.

```text
The project included [included support]. Ongoing [support type] is a separate support arrangement. I can put together [options] if you want coverage after [date].
```

Example:

```text
The redesign included launch support through Friday. Ongoing content updates are a separate support arrangement. I can put together two monthly options if you want coverage after launch week.
```

## Pattern 5: Clarify Before Committing

Use when the request is ambiguous and the freelancer is not ready to say yes or no.

```text
Before I can commit, I need to understand [specific unknown]. Can you send [needed detail]? Once I have that, I can confirm scope, timing, and cost.
```

Example:

```text
Before I can commit, I need to understand which dashboard metrics you mean and where the data is coming from. Once I have that, I can confirm scope, timing, and cost.
```

## Tone Rules

Keep the final message:

- Short.
- Warm.
- Specific.
- Non-apologetic.
- Focused on the next step.

Avoid:

- "Sorry, but..."
- "Unfortunately..."
- "I can maybe..."
- "Just this once..."
- Long explanations.
- Blaming the client.
- Defensive contract citations unless needed.
